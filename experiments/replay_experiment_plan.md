## 0.（＋）前提整備と評価プロトコルの定義

- 評価指標（2026-07-21 決定）: 各ドメイン学習後に (a) 現ドメインの適応 mAP、(b) COCO2017 のゼロショット検出性能（ZCOCO）、(c) 過去に学習した各ドメインごとの検出性能。
- 忘却指標（2026-07-21 決定）: 忘却は**個々のドメインごとに計算**する。**全ドメインでの平均は取らない**（ドメイン別に個別に見る）。
- seed=0 固定（標準 config は未設定なので明示的に追加）。
- 参照データの形式: **OD 形式に決定**（2026-07-21）。参照は OD の多クラス（Objects365=365クラス）で全クラス連結は `max_text_len` を超えるため、**負例サンプリング（`RandomSamplingNegPos`）が必須**。
- テキスト入力方式（2026-07-21 決定）: **ドメイン側も負例サンプリングに統一**する。全ドメイン・参照を OD-ODVG 形式に変換し、`RandomSamplingNegPos`（正例＋同一ドメインからサンプリングした負例）で学習する。負例はドメインごとの label_map に閉じる（同一ドメイン限定）。
  - 帰結: これにより参照とドメインが同一形式（`tokens_positive` を持つ）になり、混合が綺麗になる（loss() の分岐が一致）。一方、**現行の finetune（全クラス連結・CocoDataset）とは学習条件が変わる**ため、過去実験の値はそのまま使えず、ベースラインは新 regime で（再）実行する。変化量は実装検証(c) で確認。
- 参照データの種類: **第一候補 Objects365v1（使用予定）／第二候補 V3Det**（2026-07-21 決定、量は未定）。
  - いずれも事前学習に含まれる OD データ。θ0 が既に学習済みのため、リプレイしても ZCOCO のゼロショット性を新たに損なわない（事前学習外データより安全）。
  - Objects365v1: 365 クラス（COCO 80 を包含）・~638K 画像・~10M ボックス。ZCOCO が測る汎用日常物体に最も近く、「事前学習コーパスをリプレイする」レシピに最も素直。
  - V3Det: 183,354 画像・13,204 クラスの超多語彙・細粒度（汎用日常物体より語彙の広さの保護寄り）。
  - 注（COCO 妥当性）: Objects365 は Flickr 由来で、COCO2017-val との画像単位の非重複が一次資料で未証明。確定前に COCO2017-val とのハッシュ照合を1回かけるのが安全。
  - 除外候補（COCO 画像重複のため参照に使えない）: LVIS 1.0（画像が COCO そのもの、minival ≡ val2017）、Visual Genome（~49〜51K が COCO 画像）、COCO（評価セット）。
  - 出典整理: この整理は調査（2026-07-21）による。詳細は本節末の参照データ調査メモ、または README の関連節を参照。
- 逐次学習スケジュール（2026-07-21 決定）: 各ドメインの学習設定は**既存の単一ドメイン設定を全ドメインで使用**——epoch=20、milestones=[15]（gamma=0.1）、lr=1e-4。**各ドメインで LR スケジュールをリセット、optimizer の内部状態もリセット**（重みのみ前ドメインの last を引き継ぐ）。適応 mAP は **last** を採用。
- 負例サンプリングのパラメータ（2026-07-21 決定）: **既存（事前学習）の設定を引き継ぐ**。num_sample_negative=85 / full_sampling_prob=0.5 / max_tokens=256。
  - 注: max_tokens=256 でキャプションが常に 256 以内に収まるため、videogames（87クラス）を含め全ドメインが収まり、finetune で使っていた `max_text_len=512` は不要（contrastive_cfg も 256 と整合）。
- 実装整備: 各ドメイン＋参照の OD-ODVG 変換（ドメイン別 label_map）、`RandomSamplingNegPos` 設定、参照データ取得、混合（`ConcatDataset`）、蒸留アンカー（θ0・θ_{t-1}）の保持。
- 実装検証（要確認）: (a) OD-ODVG＋`RandomSamplingNegPos` でドメイン別 label_map の負例が同一ドメインに閉じるか、(b) 参照とドメインの混合バッチが loss() の `tokens_positive` 経路で正しく処理されるか、(c) 単一ドメイン学習の数値が現行（全クラス連結）とどれだけ変わるか、(d) 勾配疎通。

## 1. ドメインの順序決定

- **順序（2026-07-21 決定）: underwater → electromagnetic → videogames**（3ドメイン・単一順序）。
- （＋・注）順序依存に備えた複数順序は当面採らない（単一順序）。videogames は ODinW-13 に無いドメインで空白が clean に出る（→ README「ODinW-13 と RF100 ドメインの対応」参照）。

## 2. 提案手法とベースラインの学習範囲の決定

- 従来手法（ZiRa / DitHub）は各手法固有の学習構造のまま。
- **学習範囲（2026-07-21）**: **条件A は比較手法の一種**（extraction + fusion を学習、downstream 凍結）。今回のスコープ（リプレイまで）では、学習範囲の条件として **full finetuning（全モジュール）** と **条件A（extraction+fusion）** を扱う。
- **蒸留（提案手法）とその学習ベース（条件A か full FT か）は本スコープ外・未決**（後段で、結果を見てから決定）。

## 3.（＋）参照データ・バッファ・混合比率の仕様

- 参照データの種類（形式 OD、第一候補 Objects365v1〔使用予定〕・第二候補 V3Det。詳細は 0. 参照）。
- **バッファサイズ（ハイパラ）**: 参照データと各学習済みドメインのバッファサイズは**ハイパラとして指定**する。**初期設定: 参照データ 1,000、各ドメイン 500**（2026-07-21）。有効性は小バッファ域で最も出るため、掃引の対象にもなる（計画5 参照）。
- **混合方法（2026-07-21 決定）**: 参照データと過去ドメインのデータは**すべて「バッファ内データ」として扱う**。現在ドメインのミニバッチに、バッファ内データを一定割合で追加する。
  - **比率（決定）**: 現在ドメイン : (過去＋参照バッファ) ＝ **1 : 0.5**（初期値、ハイパラで指定可能）。
  - **バッファからの取り出し（決定）**: ランダム。
  - **バッファ充填（決定）**: 各ドメイン学習後、そのドメインから **ランダム**に保存（軸1＝選択方法の後回しに対する当面の既定）。
  - **探索範囲（決定）**: 混合比率・バッファサイズの**探索範囲は結果を見てから決定**（初期値のみ確定）。
  - 注: この設計では参照:過去の比は buffer 構成（初期設定なら 参照 1,000 ＋ 過去 500×(t−1)）で決まり、t が増えると参照の占める割合が縮む。t 増加時の配分の扱いは、必要になれば別途検討。

## 4. 逐次ドメインでの学習と評価（比較相手の整備）〔ユーザー項目3〕

- **比較手法（2026-07-21 決定）**: 逐次順（underwater → electromagnetic → videogames）で以下を学習・評価する。**いずれもリプレイを付ける**。
  - **ZiRa ＋ リプレイ**
  - **DitHub ＋ リプレイ**
  - **full finetuning ＋ リプレイ（＝素朴リプレイ。同一）**（全モジュール）
  - **条件A ＋ リプレイ**（extraction+fusion）
  - **リプレイの組み込み（2026-07-21 決定）**: 各手法に通常通りバッファを混ぜる。ただし **DitHub は、参照データにのみ含まれるクラス（学習ドメインに無い）は凍結モデルのみを通し、他ドメインと共通で LoRA モジュールがあるクラスのみ LoRA に通す**（DitHub の名前ベースのモジュール選択に従う）。
  - **要対応**: テキストを負例サンプリングに統一したため、全比較手法を新 regime（負例サンプリング）で（再）実行する。既存の exp_020/021（全クラス連結）はそのままは使えない。
- 全ドメイン同時学習（joint、オラクル上限）は**仮採用**——余裕があれば実行。
