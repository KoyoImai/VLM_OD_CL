## 0. 位置付け

これまでの蒸留E(exp_028 系)は「リプレイあり・蒸留は**バッファ由来サンプルに限定**」
という 1 構成のみで測られてきた。本実験はこれを 2 方向に分解する:

- **条件1(kdEonly)**: リプレイを外し、**蒸留のみ**を現在ドメインのミニバッチに適用する。
  リプレイフリー(exp_024＋exp_040)との差分が「蒸留の有無」だけになる。
- **条件2(kdEall)**: リプレイは既存のまま、蒸留を**バッチ全サンプル**
  (現在＋汎用＋過去)に広げる。exp_035 との差分が「蒸留の適用範囲」だけになる。

これで次の表が埋まり、リプレイと蒸留の寄与を分離して読める:

| | 蒸留なし | 蒸留(バッファのみ) | 蒸留(全サンプル) |
|---|---|---|---|
| リプレイなし | exp_024＋exp_040 | —(定義不能) | **exp_048 条件1** |
| リプレイあり [4,1,1]×6 | exp_027＋exp_040 | exp_035＋exp_040 | **exp_048 条件2** |

## 1. 目的

条件1・条件2 の 2 条件を、underwater → electromagnetic → videogames → aerial →
microscopic → documents の 6 ドメインで逐次学習・評価する(2026-08-20 確定)。
**仮説と判定基準は note17 でユーザーが確定する。**

## 2. 条件

### 2.1 共通の学習枠(既存 RF100 系列と同一)

| 項目 | 値 |
|---|---|
| epoch / スケジュール | 20 epoch、MultiStepLR milestones=[15]、gamma=0.1 |
| optimizer | AdamW lr 1e-4 / weight_decay 1e-4、grad clip 0.1(L2) |
| dn / num_classes / seed | 有効 / 256 / 0 |
| データ | ODVGDataset ＋ RandomSamplingNegPos(既存系列と同一) |
| 逐次方式 | 各ドメインの last(epoch_20)を次の load_from に。in-training val なし |
| 実行 | MPRG クラスタ、4 GPU × 2 ジョブ並行(条件ごとに 1 ジョブ) |

### 2.2 蒸留の仕様(両条件共通。exp_028/035 の系列と同一の定式化)

| 項目 | 値 |
|---|---|
| 検出器 | `KDGroundingDINO`(既存。直接蒸留・projector 無し) |
| 蒸留点 | 蒸留E: img(neck 出力)・txt(text_feat_map 出力)・fus(enhancer 出力 memory / memory_text)の 3 項平均。fus は画像側・テキスト側の 0.5 和 |
| 損失 / λ | L2(FeatureDistillLoss)/ **10**(const。exp_035 と同一)|
| 教師 | θ_{t-1}(t=1 は θ0 の実パス)。ドライバが model.teacher_ckpt で渡す |
| 蒸留対象 | **ミニバッチ全サンプル**。`num_buffer_per_batch` をバッチサイズ(条件1: 4、条件2: 6)に設定 → 末尾スライスが全体になる(蒸留E+ が使用済みの機構。新規コード無し)|

**t=1 の規約の差**: exp_028 の規約は「t=1 は教師 θ0 で**汎用バッファ**に蒸留」だった。
本実験の t=1 は、条件1 が現在ドメイン 4 枚(バッファ無し)、条件2 が
[現在4, 汎用2] の全 6 枚に蒸留する。t=1 から現在ドメイン入力上で θ0 への
引き留めが働く点が既存系列との違いであり、読みどころの一つ。

### 2.3 条件1: kdEonly(リプレイ無し・蒸留のみ)

- データ: 現在ドメインのみ。**batch 4/GPU・DefaultSampler**(4 GPU 合計 16。
  exp_024/exp_040 replayfree と同一)。学習 config はデータ・スケジュールとも
  exp_024 の `fullft_replayfree_<domain>.py`(前半3)と exp_040 の
  `replayfree_<domain>.py`(後半3)を継承し、モデルだけ差し替える(exp_045 と同じ構造)。
- 蒸留: バッチ全 4 枚(= 現在ドメインのデータ)に適用。`num_buffer_per_batch=4`。
- バッファ・過去データは一切使わない。

### 2.4 条件2: kdEall(リプレイあり・全サンプル蒸留)

- データ: **バッチ [現在4, 汎用1, 過去1]×6/GPU**(t=1 は [現在4, 汎用2]。
  4 GPU 合計 24。exp_035 系列と同一)。学習 config は exp_023 の
  `fullft_replay_<domain>.py`(前半3)と exp_040 の `replay_<domain>.py`(後半3)を
  継承し、モデルだけ差し替える。バッファも既存物
  (exp_023 の汎用 Objects365 1,000・各ドメイン 500、seed 0)をそのまま使う。
- 蒸留: バッチ全 6 枚(現在4＋バッファ2)に適用。`num_buffer_per_batch=6`。
- exp_035(蒸留はバッファ 2 枚のみ)との差分は蒸留の適用範囲だけ。

### 2.5 実装上の注記

- `num_buffer_per_batch >= bs` のとき、親クラスの `_assert_buffer_slice`
  (バッファ位置の毎 iteration 検査)は検査対象なしで早期 return する(実装済みの
  挙動。kd_proj_grounding_dino.py の docstring に記載)。条件2 では「先頭の現在
  ドメインにも蒸留が掛かっていること」を実行前検証で直接確かめる(§4.2)。
- 条件1 は MultiSourceSampler を使わないため、バッファ位置の前提そのものが無い。

## 3. 判定材料

**最終的な判定はユーザーが行う(note17)。**

1. 各 t(1〜6)での学習済み全ドメイン mAP と ZCOCO(評価 config は既存:
   前半3 = exp_023、後半3 = exp_026、ZCOCO = eval_base_coco)。
2. 条件1 vs リプレイフリー(exp_024＋exp_040): リプレイ無しでの蒸留の忘却抑制効果。
3. 条件1 vs exp_035＋exp_040(蒸留＋リプレイ): 蒸留があるときのリプレイの追加寄与。
4. 条件2 vs exp_035＋exp_040: 蒸留の適用範囲(バッファのみ → 全サンプル)の効果。
   特に現在ドメインへの蒸留が適応(自ドメイン mAP)を抑えるか。

## 5. 実行環境とコスト

**MPRG クラスタ、2 ジョブ並行**(各 4 GPU、a6000_ada、`--exclude=node03`)。
作業ディレクトリ(クローン)は投入時に確定する(§7 の承認後に README に記載)。

コストの根拠: 現在ドメインは両条件とも 4 枚/GPU なので iters/epoch は
replayfree と同一(6 ドメイン合計 5,025 iters/epoch × 20 epoch ≒ 100,500 iters)。
スループットの参考実測は exp_043 kdE(batch 8・教師 forward あり・クラスタ)の
約 4.5 s/iter と、本環境 A100 での kdE 系 1.5〜1.9 s/iter(2 GPU)。教師 forward の
分だけ replayfree(exp_045 見積り 40〜45 h)より重い。

| ジョブ | 内容 | 見積もり |
|---|---|---:|
| `exp048_kdEonly` | 条件1 6 ドメイン＋評価 | 約 60〜90 h |
| `exp048_kdEall` | 条件2 6 ドメイン＋評価 | 約 80〜110 h |

見積もりの不確かさが大きいため `--time=168:00:00`(上限)とする。ドライバは
epoch_20.pth の有無でスキップ判定し、途中停止しても同じコマンドで再開できる。
ディスクは ckpt 約 2 GB × 20 epoch × 6 ドメイン × 2 条件 ≒ 約 480 GB。
保持方針は**全 epoch 保持**(継承既定のまま。2026-08-20 ユーザー決定)。

## 6. リスク・懸念

- **条件1 の t=1**: 蒸留と検出損失が同一データ(現在ドメイン)に掛かるため、
  θ0 への引き留めと適応が直接競合する。適応 mAP が既存系列より下がる可能性が
  あるが、それ自体が測定対象である。
- **条件2 の蒸留損失のスケール**: 蒸留対象が 2 枚 → 6 枚になるが、損失は
  サンプル平均(式(7)の 1/n)なので λ=10 の意味は変わらない。ただし現在ドメイン
  サンプルの勾配に蒸留項が加わる点は exp_035 と異なる。
- checkpointing は継承既定のまま(num_cp=6・Swin with_cp=True)。KDGroundingDINO は
  教師側のみ cp を剥がす実装で、DDP との衝突は exp_035/043/046 で発生していない
  (EWC と違い θ を forward 外で使わないため)。

## 7. 承認をお願いする範囲

§2 の条件で、条件1(kdEonly)・条件2(kdEall)を RF100 6 ドメインで逐次学習・
評価すること。実行は MPRG クラスタ 2 ジョブ。本環境で行うのは config 作成と
実行前検証(§4.2)まで。ckpt は全 epoch 保持(§5。2026-08-20 確定)。
