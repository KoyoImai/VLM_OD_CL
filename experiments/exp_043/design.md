## 0. 位置付け

既存のリプレイ（exp_027＋exp_040）と蒸留E＋リプレイ（exp_028/035＋exp_040）は
バッチ 6/GPU・構成 [現在4, 参照1, 過去1] で測られている。本実験は note13 の指定に従い、
**バッチ構成を [現在4, 汎用2, 過去2]（バッチ 8/GPU、4 GPU 合計 32）に変えた別パターン**で、
リプレイのみと蒸留E＋リプレイの 2 条件を **6 ドメイン頭から通しで**学習・評価する。

既存系列との差分は次の 3 点に絞られる（それ以外は同一）:

1. **バッチ構成**: [4, 1, 1]×6 → **[4, 2, 2]×8**。t=1 は [現在4, 参照2]（batch 6）→
   **[現在4, 汎用4]（batch 8）**。現在ドメインは 4/GPU のままなので iters/epoch は不変。
2. **蒸留対象の枚数**: バッチ末尾のバッファ由来 2 枚 → **4 枚**（t≥2: 汎用2＋過去2、
   t=1: 汎用4）。「蒸留はバッファ内データに限定」「t=1 は教師 θ0 で汎用バッファに蒸留」
   という規約自体は exp_028 と同一（exp_028 design §3・§4）。
3. **6 ドメイン通し**: 既存は前半3（exp_027/028/035）＋接続（exp_040）だが、本実験は
   θ0 から 6 ドメインを 1 本で走らせる。

## 1. 目的

note13 の条件で、リプレイのみ／蒸留E＋リプレイの 2 条件を 6 ドメイン逐次
（underwater → electromagnetic → videogames → aerial → microscopic → documents）で
学習・評価する。**仮説と判定基準は note13 でユーザーが確定する。**

## 2. 条件

### 2.1 共通の学習枠（既存 RF100 系列と同一。2026-08-16 確定）

| 項目 | 値 |
|---|---|
| 学習対象 | 全モジュール（条件A。Swin/BERT は継承どおり lr_mult=0.1） |
| epoch / スケジュール | 20 epoch、MultiStepLR milestones=[15]、gamma=0.1 |
| optimizer | AdamW lr 1e-4 / weight_decay 1e-4、grad clip 0.1（L2） |
| dn / num_classes / seed | 有効 / 256 / 0 |
| データ | ODVGDataset ＋ RandomSamplingNegPos（exp_023 と同一） |
| 逐次方式 | 各ドメインの last（epoch_20）を次の load_from に。in-training val なし |
| 実行 | **MPRG クラスタ、4 GPU × 2 ジョブ並行**（2026-08-16 確定） |

### 2.2 バッチ構成（本実験の核。note13）

| | ソース | source_ratio | batch/GPU | 合計（4 GPU） |
|---|---|---|---:|---:|
| t=1 | [現在, 汎用] | [4, 4] | 8 | 32 |
| t≥2 | [現在, 汎用, 過去プール] | [4, 2, 2] | 8 | 32 |

- サンプラは既存の `CurrentEpochMultiSourceSampler`（ソース順がバッチ内で保存される）。
- 過去プールは学習済みドメインの累積（各 500 枚を ConcatDataset で 1 ソースに、
  そこからランダムに引く）。exp_040 §2.4 と同じ構造で比率だけ 1→2。
- 現在ドメインは 16 枚/step で従来と同じなので、epoch あたりの iteration 数・
  DitHub 等との学習量対応は変わらない。バッファ側の消費だけが 8→16 枚/step に増える。

### 2.3 バッファ（既存物を再利用）

- 汎用ドメイン: Objects365v1 **1,000 枚**（`experiments/exp_023/buffer/reference_o365v1_1000.odvg.json`）
- 各ドメイン: **500 枚**（`experiments/exp_023/buffer/<domain>_500.odvg.json`）
- いずれも **seed 0 のランダム選択**で作られたことを manifest で確認済み（2026-08-16。
  note13 の「ランダム選択」の指定を満たす）。exp_027/035/040 とバッファが同一なので
  バッチ構成だけの差分で比較できる。

### 2.4 蒸留E条件（exp_028/035/040 の系列と同一の定式化）

| 項目 | 値 | 経緯 |
|---|---|---|
| 検出器 | `KDGroundingDINO`（既存） | exp_028 実装 |
| 蒸留対象の特徴 | 画像・テキスト・融合後の 3 特徴（蒸留E） | note13 |
| 形式 / λ | L2 / **10** | note13。exp_035/040 と同一 |
| 教師 | θ_{t-1}（**t=1 は θ0**）。ドライバが `model.teacher_ckpt` で渡す | note13。t=1 蒸留は exp_028 と同じ規約（θ0 を動かさない制約として働く） |
| 蒸留データ | **バッチ末尾のバッファ由来 4 枚に限定**（`num_buffer_per_batch=4`） | note13。KDGroundingDINO は「バッチ末尾 n 件＝バッファ」という規約で識別（実装確認済み 2026-08-16）。従来は 2 枚 |
| 適用期間 | 全 epoch | exp_028 と同一 |

## 3. 判定材料

**最終的な判定はユーザーが行う（note13）。** 数値の閾値は設けない。

1. 各 t（1〜6）での学習済み全ドメイン mAP と ZCOCO。
2. 条件間（replay vs kdE）の対照＝蒸留の寄与。
3. 既存バッチ構成の系列との対照: リプレイは exp_027＋exp_040、蒸留Eは
   exp_028(λ調整)/exp_035＋exp_040。バッファが同一なので差分はバッチ構成
   （と 6 ドメイン通しか接続か）に帰着する。

### 4.3 実行前に確認する項目（本環境）

1. 12 本の config が build でき、学習設定が §2.1 と一致（機械的 diff を含む）
2. バッチ構成: 実データでバッチを引き、[現在4, 汎用2, 過去2]（t=1 は [現在4, 汎用4]）の
   順序・枚数になっていること（img_path とバッファ JSON の突き合わせ）
3. kdE: `num_buffer_per_batch=4` でバッチ末尾 4 枚がバッファ由来であることの assert が通り、
   蒸留損失が末尾 4 枚だけに掛かること。teacher_ckpt が `--cfg-options model.teacher_ckpt=`
   で届くこと（exp_040 項目 10 と同じ負テスト込み）
4. 実データ 1 step で loss（kdE は loss_kd 込み）が有限であること（t=1 と t≥2 の両構成）
5. VRAM: バッチ 8/GPU（kdE は教師 forward 込み）が A6000 48GB に収まることの実測
6. クラスタ側パスで config が解決すること（/local_cache ステージング前提）

## 6. リスク・懸念

- **合計バッチ 24→32 で lr は据え置き**（1e-4。線形スケーリングしない）。
  「ハイパラは既存系列と同じ」というご指示（2026-08-16）に従った帰結で、
  バッチ構成の効果と最適化の効果は本実験では分離しない。
- **KD のバッチ末尾規約**はサンプラの実装（ソース順保存）に依存する。§4.3 項目 2・3 で
  実データにより検証する（exp_028 でも同じ規約で検証済み）。
- kdE の VRAM はバッチ 8 ＋ 教師 forward で従来（batch 6 で 14.4 GB）より増える。
  §4.3 項目 5 で実測し、A6000 48GB に収まることを確認してから投入する。
